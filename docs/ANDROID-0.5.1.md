# Android 0.5.1: guided logging and useful insights

Log remains a chat. Its empty-state introduction lists all eight supported categories: food/drinks, medication/supplements, sleep, activity/exercise, water, mood, body measurements, and notes for other facts.

The AI asks focused follow-ups until essential facts are available. Food needs identity, consumed quantity/unit and a defensible calorie estimate; material brand/preparation/portion assumptions must be confirmed. Plain food photos always require actual-portion confirmation. The server also refuses to save incomplete food, activity (no duration or steps), sleep (no duration), medication (no dose), water and measurement data. A mixed batch is held until clarified, so retries do not save partial duplicates. Unknown is never converted into zero. Explicitly declined food detail can be logged as a note rather than a calorie-bearing food estimate. Exercise details such as intensity, sets/reps/load are retained in notes; activity calories are not invented.

Each task has a compact AI-produced factual continuation instead of an ever-growing chat replay. Log and Insights have separate account/backend-scoped private continuation files. Pending questions survive process recreation; the question and factual state are sent on the next answer. There is no fixed follow-up turn count. The state and existing message limits remain bounded, so this is not a guarantee that model summaries can never omit a fact. Starting a new log clears its pending clarification. Continuations and pending messages older than three calendar months are removed during existing retention maintenance.

Insight intent clarification may now occur before dates are resolved. Clear summaries do not need redundant questions. After database retrieval, a second AI step produces a concise interpretation grounded in retrieved aggregates, up to 50 reference records and any explicitly shared profile. It may ask a further question when the comparison/goal is unclear. Missing intake/logs remain unknown; a partial food subtotal cannot establish a calorie deficit, adherence or health status. Tables remain visible alongside the response.

You always shows Age and Gender, with age calculated from date of birth. Height/weight controls remain simple. The Daily calorie target card starts a separate AI interview after a profile-sharing consent dialog. Age, height and weight are required; gender identity never selects an energy-equation coefficient. The interview asks for explicit physiology choice, usual activity, maintain/lose/gain goal and circumstances making a generic estimate inappropriate. Users may decline. The server calculates Mifflin–St Jeor maintenance from confirmed inputs, rounds to 50 kcal and uses a modest 250 kcal adjustment for a lose/gain starting target. It rejects underweight weight-loss requests and estimates below conservative application floors (1500 male/1200 female), below calculated BMR or above 10000. These are application guardrails, not clinical thresholds or a medical prescription. The user must accept a proposed target. A target is an estimate, not a hard maximum. Profile/measurement changes invalidate it; targets/interviews are account/backend-bound. Shared target context includes an effective date, not a retroactive allowance.

Profile and target files remain on the device. Only after enabling profile sharing are age, gender, height, weight and an accepted dated target sent with AI requests. Setup can stop future sharing. The calorie interview does not create journal entries. The API still holds all paid OpenAI credentials server-side. New journal response fields are opt-in with X-MetricMe-Features: guided-journal-v1; 0.4.0, 0.4.1 and 0.5.0 strict parsers retain compatible responses.

Sources informing implementation: [NIDDK Body Weight Planner](https://www.niddk.nih.gov/health-information/weight-management/body-weight-planner), [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [OpenAI conversation state](https://developers.openai.com/api/docs/guides/conversation-state). The implementation uses explicit compact context and store=false, not a provider-hosted conversation.

Validation and deployment: pending. Automated fake-upstream tests do not establish live model judgment quality; a signed-in phone check remains necessary.
